# Repository Guidelines

## Project Structure & Module Organization

This is a browser game built with React, TypeScript, Vite, and TanStack Start. Application code lives in `src/`: route components are in `src/routes/`, reusable screens and UI are in `src/components/`, gameplay logic and modes are in `src/game/`, and shared hooks/utilities are in `src/hooks/` and `src/lib/`. Game art and sprites belong in `src/assets/`; static files served as-is belong in `public/`. Tests and their setup are in `src/test/`. `src/routeTree.gen.ts` is generated by the router plugin; make route changes in `src/routes/`, not in the generated file.

## Build, Test, and Development Commands

Use npm (the repository includes `package-lock.json`):

- `npm install` installs dependencies.
- `npm run dev` starts the local Vite development server.
- `npm run build` creates the production build.
- `npm run preview` serves the built app locally for inspection.
- `npm test` runs the Vitest suite once; `npm run test:watch` keeps it running during development.
- `npm run lint` runs ESLint; `npm run format` applies Prettier formatting.

## Coding Style & Naming Conventions

Follow the existing TypeScript and React patterns. Prettier uses two-space indentation, double quotes, semicolons, trailing commas, and a 100-character print width. Use PascalCase for React components (for example, `GamePage.tsx`), camelCase for functions and variables, and descriptive kebab-case or existing naming patterns for route files. Keep gameplay rules in `src/game/` rather than mixing them into route components. Run `npm run lint` and format changed files before submitting.

## Testing Guidelines

Tests use Vitest with a jsdom environment and Testing Library. Place tests under `src/` and name them `*.test.ts` or `*.test.tsx` (or `*.spec.*`); `vitest.config.ts` discovers those patterns. Add or update tests for behavior changes, especially routing and gameplay interactions. No repository-wide coverage threshold is configured.

## Commit & Pull Request Guidelines

Recent commits use short, imperative summaries, often prefixed with an action such as “Fix” or “Improve”; some use Portuguese. Keep each commit focused and its subject concise. Pull requests should explain player-visible changes, list relevant checks run, link related issues when available, and include screenshots or a short recording for visual or control changes. Call out any changes to controls, routes, or game balance.

## Configuration

Do not commit secrets or local environment files. Keep dependencies reproducible by updating the lockfile when changing `package.json` dependencies.
